# گزارش فنی بررسی ساختار فایل‌ها و سازوکار رمزگشایی در جامع‌الاحادیث ۴

## خلاصه 

این گزارش روند بررسی فایل‌های ارائه‌شده، شناسایی نرم‌افزار تولیدکننده، تحلیل ساختار داخلی برنامه و در نهایت شناسایی سازوکار رمزنگاری و فشرده‌سازی داده‌ها را توضیح می‌دهد. هدف از این بررسی، درک این موضوع بود که داده‌های موجود چگونه ذخیره می‌شوند و نرم‌افزار در زمان اجرا چگونه آن‌ها را برای استفاده آماده می‌کند.

در شروع، فایل `encode_text.txt` با روش‌های معمول رمزگشایی متن بررسی شد، اما هیچ‌کدام از encodingهای آزمایش‌شده نتیجه قابل استفاده‌ای نداشتند. بررسی آماری داده‌ها نشان داد که محتوای فایل ظاهری شبیه داده‌های رمزنگاری‌شده دارد.


## ۱. بررسی اولیه فایل

در نخستین مرحله، فایل جدید `encode_text.txt` بررسی شد و روش قبلی با عنوان `v1` روی آن اجرا شد. این روش با خطا مواجه شد و خروجی قابل استفاده‌ای تولید نکرد.

### ۱.۱. آزمایش encodingهای مختلف

برای اطمینان از اینکه مشکل صرفاً ناشی از تفسیر نادرست متن نیست، چند encoding رایج از جمله موارد زیر آزمایش شدند:

- `Latin-1`
- `UTF-8`
- `UTF-7`
- چند روش متداول دیگر برای تفسیر داده‌های متنی

هیچ‌کدام از این روش‌ها محتوای معناداری تولید نکردند. این نتیجه نشان می‌داد که احتمالاً مسئله فقط انتخاب encoding نیست و داده‌ها پیش از تبدیل به متن، با روشی دیگر پردازش شده‌اند.

### ۱.۲. بررسی آنتروپی یا بی نظمی متن

در مرحله بعد، آنتروپی فایل بررسی شد. آنتروپی معیاری آماری برای سنجش میزان پراکندگی و پیش‌بینی‌ناپذیری مقادیر داده است. در فایل‌های متنی معمولی، معمولاً الگوهای تکرارشونده بیشتری وجود دارد؛ اما داده‌های فشرده یا رمزنگاری‌شده اغلب پراکندگی بالاتری نشان می‌دهند.

مقدار مشاهده‌شده حدود `7.8 از 8` بود. این مقدار بالا با داده‌های فشرده یا رمزنگاری‌شده سازگار است، اما **به‌تنهایی اثبات نمی‌کند که الگوریتم خاصی مانند AES یا DES استفاده شده است**. برای تعیین روش دقیق، لازم بود برنامه‌ای که فایل را تولید یا مصرف می‌کند بررسی شود.

### ۱.۳. فرضیه اولیه و محدودیت بررسی

پس از این مرحله، فرضیه اصلی این شد که فایل با یک سازوکار رمزنگاری پردازش شده و برای بازسازی روند، باید نحوه تولید کلید (`key`) و بردار مقداردهی اولیه (`IV`) مشخص شود. بخش‌های ابتدا و انتهای متن نیز بررسی شدند، اما کلید یا IV در داخل متن پیدا نشد.

این نتیجه باعث شد مسیر بررسی از آزمایش encodingهای عمومی به سمت منطق پشت رمزنگاری آن و نرمافزار تولید کننده پیش برود.

## ۲. شناسایی نرم‌افزار تولیدکننده داده‌ها

برای مشخص شدن منشأ فایل‌ها، درباره نرم‌افزاری که آن‌ها را ایجاد می‌کند اطلاعات بیشتری جمع‌آوری شد. در نهایت، بررسی به محصولات مؤسسه نور و به‌ویژه نرم‌افزارهای این مجموعه رسید.

وب‌سایت مرتبط: [noorshop.ir](https://www.noorshop.ir/)

مشخص شد ک برنامه‌ای ک این متن رو تولید کرده نرم‌افزار **جامع‌الاحادیث ۴** است. ولی از آنجایی ک حجم ان زیاد بود و 11 گیگ بود.
و با فرض اینکه نرم‌افزار های این مجمعه ساختاری مشترک دارن و فقط توی محتوا های متنی متفاوت هستن به جای **جامع‌الاحادیث ۴** نرم‌افزار **حافظ** رو نصب کردیم.

### ۲.۱. بررسی ساختار نرم‌افزار حافظ

در بررسی اولیه نرم‌افزار حافظ، ساختار رابط کاربری با روش‌های رایج برنامه‌های ویندوزی تفاوت‌هایی داشت. نشانه روشنی از استفاده مستقیم از کنترل‌های متداول GDI+ یا یک صفحه HTML داخلی در بخش‌های بررسی‌شده مشاهده نشد؛ به نظر می‌رسید نمایش محتوا تا حدی بر پایه جابه‌جایی عکس های مختلف میباشد. و جدا از اون توی requirement های برنامه adobe flash وجود داشت.

فایل‌های محتوایی اصلی دارای پسوند `.cfd` بودند. بررسی محتوای داخلی آن‌ها نشان داد که پسوند فایل لزوماً نوع واقعی داده را مشخص نمی‌کند: برخی فایل‌ها با امضای فایل‌های PNG، برخی با BMP، برخی با TTF و برخی با قالب‌های دیگر سازگار بودند.

برای شناسایی نوع واقعی فایل‌ها از ابزار **TrID** استفاده شد. این ابزار با بررسی امضاها و الگوهای داخلی فایل، نوع احتمالی آن را تخمین می‌زند. این بررسی نشان داد که فایل‌های دارای پسوند یکسان ممکن است درون خود انواع متفاوتی از منابع را نگهداری کنند.

### ۲.۲. بررسی رفتار برنامه

برای درک بهتر نحوه اجرای برنامه، ساختار اجرایی آن نیز بررسی شد. ابزار **x64dbg** برای بررسی رفتار برنامه در سطح پایین‌تر و مشاهده بخش‌هایی از اجرای آن به کار رفت. این مرحله به شناخت اولیه ساختار برنامه کمک کرد، اما سازوکار رمزگشایی موردنظر از همین بررسی به‌تنهایی مشخص نشد.

خلاصه نرم‌افزار حافظ این بود ک ما یه اشتراک براش خریدیم ک ببینم چطور کار میکنه کلی هم ساختارش رو بررسی کردم ک کد فعالسازیش رو پیدا کنیم. یا اینک روش ساختش رو مهندسی معکوس کنیم. ولی ناموفق بود.

## ۳. بررسی نرم‌افزار جامع‌الاحادیث ۴

### ۵.۱. شناسایی فرایند Node.js

در زمان اجرای برنامه، فرایندی با نام `node.exe` مشاهده شد. مسیر آن در محیط آزمایش چنین بود:

`C:\Program Files (x86)\Noor\Core32S.1.7.2.6357\Node.js\node.exe`

برای مشاهده شناسه فرایند (PID) و خط فرمان اجراشده، از PowerShell و دستور زیر استفاده شد:

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
  Select-Object ProcessId, CommandLine
```

خروجی این دستور دو داده مهم در اختیار می‌گذارد:

- **ProcessId:** شناسه‌ای که سیستم‌عامل برای شناسایی همان فرایند در نظر گرفته است.
- **CommandLine:** مسیر برنامه و آرگومان‌هایی که هنگام اجرا به آن داده شده‌اند.

نمونه‌ای از خط فرمان مشاهده‌شده:

```text
"C:\Program Files (x86)\Noor\Core32S.1.7.2.6357\Node.js\node.exe"
main.js --port 9240 --appId JamiAhadith4
--programDataPath Z:/ProgramData/Noor/JamiAhadith4/elasticdata/Program
--localAppDataPath C:/Users/81/AppData/Local/Noor/JamiAhadith4
--parentProcessId 19892
--elasticUrl http://localhost:9201
```

از این آرگومان‌ها می‌توان دریافت که سرویس با شناسه برنامه `JamiAhadith4` اجرا می‌شود، از مسیرهای مشخصی برای داده‌ها استفاده می‌کند و به یک سرویس Elasticsearch در نشانی محلی `http://localhost:9201` متصل می‌شود. شماره پورت، مسیرها و شناسه فرایند نمونه‌های مربوط به محیط بررسی‌شده‌اند و ممکن است در اجرای دیگر متفاوت باشند.

## ۷. بررسی درخواست‌های Elasticsearch و یافتن منطق پردازش داده

- `node:buffer` برای نگهداری و پردازش داده‌های باینری.

- `node:zlib` برای فشرده‌سازی و بازکردن فشرده‌سازی.

      } catch (o) {

        return (console.error("Error during decompression:", o), null);

      }

    }

    static encrypt(e) {

      let n = sg.Buffer.from(e);

      return this.processCipher(n, !1).toString("base64");

    }

    static decrypt(e) {

      let n = sg.Buffer.from(e, "base64");

      return this.processCipher(n, !0).toString();

    }

    static encryptWithCompression(e) {

      let n = sg.Buffer.from(e),

        r = this.compressData(n);

      return this.processCipher(r, !1).toString("base64");

    }

    static decryptWithCompression(e) {

      if (!e) return;

        r = this.processCipher(n, !0);

      return this.decompressData(r)?.toString();

    }

  };

import base64

from cryptography.hazmat.primitives import padding
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes


def decrypt_aes_128_cbc(ciphertext: bytes, key: bytes, iv: bytes) -> bytes:
    """Match Node: createDecipheriv("aes-128-cbc", key.slice(0, 16), iv) with auto padding."""
    key16 = key[:16]
    if len(key16) != 16:
        raise ValueError("key must be at least 16 bytes")
    if len(iv) != 16:
        raise ValueError("IV must be 16 bytes")
    if len(ciphertext) == 0 or len(ciphertext) % 16 != 0:
        raise ValueError("ciphertext length must be a positive multiple of 16")

    decryptor = Cipher(algorithms.AES(key16), modes.CBC(iv)).decryptor()
    padded = decryptor.update(ciphertext) + decryptor.finalize()
    unpadder = padding.PKCS7(128).unpadder()
    return unpadder.update(padded) + unpadder.finalize()


def decrypt_text(encrypted: str, key: bytes, iv: bytes, encoding: str = "base64") -> str:
    if encoding == "base64":
        ciphertext = base64.b64decode(encrypted)
    elif encoding == "hex":
        ciphertext = bytes.fromhex(encrypted)
    else:
        raise ValueError("encoding must be 'base64' or 'hex'")
    return decrypt_aes_128_cbc(ciphertext, key, iv)

def decrypt_from_text(encrypted: str) -> str:
    key = b"!WeBmAsTeR@iNoOr.Ir-(1393,2014)!"  # same bytes as getKeyBuffer(); only the first 16 are used
    iv = b"!C.R.C.I.S-key#!"       # same 16 bytes as getIVBuffer()

    return decrypt_text(encrypted, key, iv)

def decompress_data(data: bytes) -> bytes:
    if len(data) < 4:
        raise ValueError("Input data is too short")
    expected = struct.unpack(">I", data[:4])[0]
    out = zlib.decompress(data[4:])
    if len(out) != expected:
